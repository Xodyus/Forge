Forge — Project Notes

Working notes from the analysis of Forge_Master_Build_Specification.docx (v1.0, 2026-07-22). Covers: what the spec contains, an assessment of it, the work breakdown, tooling and reading, how to use Claude Code on it, and where to stop for resume purposes.

1. What the document is

A ~64,000-word, 434-section master build specification: 17 Parts plus Appendices A–M. It is specification only — no code exists yet.

The spec is simultaneously a PRD, an execution-semantics contract, an architecture document, an implementation playbook, a fault-recovery design, a verification plan, a benchmark protocol, a 20-week project plan, and a portfolio-release checklist. It's explicitly framed as a portfolio project targeting an HRT Summer 2027 SWE internship, with a stated truthfulness rule: nothing goes on a resume until a tagged repo and reproducible evidence support the exact wording.

The system

A local-first, deterministic event-replay and compute engine. A client registers an immutable fixed-record dataset and an experiment. A coordinator deterministically partitions it into tasks, leases them to process-isolated workers, accepts attempt-scoped staged outputs, and conditionally commits exactly one visible result per task. Workers may crash or double-execute; committed results remain unambiguous.

Load-bearing design decisions
Decision	Why it matters
At-least-once execution, exactly-once visible commit	Physical re-execution is allowed; the guarantee is about result visibility only
Leases + fencing epochs	Stale workers cannot overwrite committed state after lease expiry
SQLite as durable coordination truth	No correctness guarantee may depend on in-memory state
Attempt-scoped staging + atomic publication	Write temp → fsync → rename; partial artifacts never become visible
Control plane separated from data plane	Scheduler messages stay small and inspectable
Framed binary protocol over UDS/TCP	Incremental decoder, bounded write queues, version negotiation, defensive limits
Narrow C++20 pybind11 accelerator	Accepted only if measurement justifies it — explicitly not assumed to be faster
Structure
Parts I–II — product definition, acceptance contract, execution semantics, invariants
Parts III–VIII — architecture, coordinator, worker runtime, storage formats, protocol, C++ boundary
Parts IX–XVI — scheduling, fault tolerance, SDK/CLI, observability, security, verification, benchmarking, build/CI/release
Part XVII — 20-week roadmap, milestone gates, backlog, risk control
Appendices A–M — code skeletons, SQL, protocol pseudocode, test and benchmark schemas, runbooks, checklists, references
2. Assessment
Strengths

Unusually strong on the things portfolio projects normally get wrong: precise vocabulary, explicit non-goals, scope-control rules, a truthfulness rule about resume claims, and a mandate to publish negative results. §4 (non-goals), §13 (scope control), and §269 (critical path) are the most valuable pages in the document. Reread them whenever tempted to add something.

Risks

Proportion. ~300–400 hours of planned work for a system whose spec is likely 10× the size of its eventual code. Gates 0–B (weeks 1–8) are realistic. Gates D–F assume no debugging surprises in C++ interop, crash-matrix flakiness, or benchmark methodology — all of which reliably eat weeks.

Spec drift. v1.1 is scheduled for after Gate A, which is correct. But if the document stops matching the code it becomes a liability in an interview rather than an asset.

Naming collision — fix in v1.1. The document uses "Gate A/B/C" twice with different meanings: §10 (release gates) and §268 (milestone gates, week-anchored). These are not the same gates. Everything below uses the §268 week-anchored numbering.

4. Libraries and tooling

Python standard library (the real substance): asyncio, multiprocessing (spawn semantics), multiprocessing.shared_memory, sqlite3, mmap, signal, struct, hashlib, resource, os (fd inheritance, rename, fsync), contextvars, dataclasses/enum, pathlib.

Python third-party: pydantic or attrs, Typer or Click, pytest + pytest-asyncio, Hypothesis, mypy or pyright, Ruff, uv (or Poetry), coverage.py, msgpack (deferred), py-spy / cProfile / memray or Scalene, pandas + matplotlib.

C++ / build: C++20 toolchain (GCC 12+ / Clang 15+), CMake ≥ 3.24 with presets, pybind11, scikit-build-core, GoogleTest or Catch2, Google Benchmark, ASan, UBSan, libFuzzer.

Systems tooling: perf, strace, lsof, ss, SQLite CLI, GitHub Actions.

Sequencing note: do the leases/fencing and crash-consistency reading before week 5, not during. Those two topics determine the SQLite schema, and §269 is right that a schema built on vague semantics is expensive to repair.

6. Accelerating with Claude Code

Realistic compression: 20 weeks → 13–15 weeks, not 20 → 6.

Where it genuinely compresses
Area	Saving	Notes
Week 1 scaffold	~1 week → 1–2 days	Fully specified target, pure mechanical setup
Test infrastructure	~2 weeks total	The plumbing, not the test cases: fixtures, deterministic clock, fault-injector scaffolding, crash-matrix runner
C++ build friction	~1 week	CMake + scikit-build-core + pybind11 + sanitizers teaches nothing and eats days
Benchmark analysis	~4 days	Once the raw record schema is frozen, the raw-JSON → tables/charts pipeline is mechanical
Documentation (weeks 18–19)	~50%	Docstrings, docs site, API reference — not the architecture narrative or limitations page
Debugging	Unquantifiable but real	Race conditions in the lease/commit path are where time actually goes
Where it doesn't

The critical path (§269) is a dependency chain of understanding, not typing. Weeks 2, 12, and 17 are thinking weeks — freezing semantics, choosing the native boundary from profile evidence, designing benchmark methodology. This is Amdahl's law applied to your own project: accelerating the parallel fraction doesn't help when the serial fraction is comprehension.

The conditional commit transaction, lease expiry with fencing epochs, and the recovery reconciliation matrix are the project. ~400 lines out of the whole repo, and the 400 lines an interviewer will pull on. If you can't re-derive on a whiteboard why a fencing epoch is checked inside the same transaction as the commit — and what breaks if it isn't — the project inverts from asset to liability.

The guard is already in the spec: §270 ends each week with "explain the design aloud," and every week section has review questions. Those become more important with AI assistance, not less. Concrete test: after each gate, close the laptop and re-derive the core mechanism on paper.

ADRs stay hand-written. They're the durable record of your judgment and what makes the interview conversation good.

Setup

Split the spec into docs/spec/part-XX.md files rather than feeding a 64k-word blob. Write a CLAUDE.md holding only load-bearing constraints: glossary (§427), invariants (§31), non-goals (§4), scope-control rules (§13), and an index of which spec file covers what.

Put the scope-control rules in CLAUDE.md verbatim — best defense against the failure mode where an agent helpfully adds speculative execution before leases are correct.

Highest-value use is adversarial review, not generation. Paste the commit transaction and ask for the interleaving that breaks it. Ask what happens if the coordinator dies between the artifact rename and the database commit. Ask it to argue the fencing check is in the wrong place. This builds understanding rather than substituting for it, and it's the closest thing a solo project has to code review.

Also: plan mode for design conversations before implementation; at Gate E, have it generate hostile interview questions from your own docs and grade answers against the §271–290 review questions.

7. Where to ship

Gate B is the floor. Gate C is the target.

Gate A (week 4) — not enough

A single-process deterministic batch job. Necessary as the oracle for everything after it, but the honest bullet is "built a deterministic data-processing pipeline with reproducible output verification." True and unremarkable. Nothing in it shows distributed-systems reasoning.

Gate B (week 8) — the floor

First point where the project stops resembling a multiprocessing tutorial. Durable coordinator, lease-based assignment with fencing, at-least-once execution with exactly-once visible commit, crash recovery a script can demonstrate.

Built a durable task coordinator with SQLite-backed state, lease-based assignment with fencing epochs, and a conditional commit protocol providing exactly-once visible results under at-least-once execution.

Automated crash tests demonstrating that worker kill, lease expiry, duplicate completion, and coordinator restart each produce deterministic, non-ambiguous committed state.

Keep the "visible" qualifier. The truthfulness rule requires it, and an interviewer who notices you kept it will think better of you than one who catches you dropping it.

Gate C (week 11) — the target

Adds the framed protocol, which is where the "systems fundamentals — memory, I/O, process management" signal actually lands. Also a coherent stopping point: the system is complete and explainable without C++.

Implemented a framed binary protocol over Unix-domain sockets with an incremental decoder state machine, bounded write queues with backpressure, and version negotiation; property- and fuzz-tested against fragmentation, coalescing, truncation, and oversized frames.

Gate D (week 14) — conditional

Matters if you want to be read as a C++ candidate rather than a Python one. Highest-variance gate — pybind11, CMake, sanitizers, and a defensible crossover measurement is a lot for three weeks. Its bullet is only strong if the measurement is honest about where native loses.

The part people skip

Whatever gate you stop at, you still owe a slice of Gate F: a README that reproduces one successful run and one recovery scenario from a clean checkout, a clean-machine rehearsal, a limitations page, and a security pass. Three to five days. It's the difference between a portfolio project and code on GitHub. Gate B plus that polish beats Gate D with a README nobody can follow.

Build the resume claim map incrementally — at each gate, write the bullets that gate supports and check each against a command you can actually run. Gate F work in ten-minute increments.

Timing constraint

As of late July 2026, twenty weeks puts Gate F in mid-December. Quant/HFT firms recruit early and a Summer 2027 class may be substantially filled before the project is "done." Gate B lands ~late September; Gate C ~mid-to-late October — much safer dates to have a shippable repo.

Likely plan: ship Gate C with release polish in October, apply, keep building D–F publicly. A repo with visible ongoing commits is a talking point, not a weakness.

⚠️ Unverified. The recruiting-timeline claim above is a general observation about the industry, not a checked fact about HRT's Summer 2027 application dates. Confirm against HRT's student-opportunities page before planning around it.

9. The one-line version

Freeze semantics before schema. Build the single-process oracle before multiprocessing. Persist before retrying. Stage before recovering. Measure before optimizing in C++. Automate failure before publishing performance. Ship Gate C in October and keep going in public.
